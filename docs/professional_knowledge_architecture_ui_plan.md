# 专业课私有知识库方案与 UI 演进建议

## 1. 目标重述

当前模块不应只停留在“PDF/OCR -> 抽取知识点”的工具层，而应逐步演进为一个可追溯、可检索、可复习、可问答的专业课私有知识库系统。

系统目标：

```text
资料导入
-> 文档解析
-> 原文事实库
-> 知识点草稿抽取
-> 用户确认
-> 私有知识库
-> 检索问答
-> 复习调度
-> 知识关系图
```

核心原则：

- 每个知识点都必须能回到 PDF 原文
- 原文、知识点、复习内容要分层存储
- OCR / 图像理解只是资料解析手段，不是系统核心
- 用户确认后的知识点才进入正式知识库


## 2. 推荐技术路线

### 2.1 四层架构

建议系统拆成四层：

1. 文档事实层
2. 知识抽取层
3. 私有知识库层
4. 复习与问答层

对应含义：

```text
文档事实层
  存原始资料的“可引用事实”
  例如：第12页题43、某段原文、某张结构图、某个表格

知识抽取层
  从事实层中抽取候选知识点
  但不直接替代事实层

私有知识库层
  保存用户确认后的知识点
  带来源、标签、优先级、掌握状态

复习与问答层
  对知识点与事实层做联合检索
  支持问答、复习卡、追问、关系图
```

### 2.2 资料解析链路

推荐链路：

```text
PDF
-> MinerU 解析
-> 版面块 / 表格 / 图片 / 页码 / bbox
-> 文本清洗
-> source_chunks 入库
-> 图片轻量过滤
-> 高价值图表送 VLM
-> 图表结构化结果入库
-> 再做知识点抽取
```

这里建议：

- `MinerU` 负责复杂 PDF 版面解析
- `PaddleOCR` 作为扫描件 / 本地兜底能力保留
- `CLIP` 或轻量图分类只做图片筛选，不做核心知识抽取
- `VLM` 只处理有价值图、表、结构图、拓扑图、流程图

### 2.3 图片处理顺序

不建议直接：

```text
MinerU -> VLM 分类 -> CLIP 过滤
```

更合适的是：

```text
MinerU
-> 规则过滤
-> imagehash / 重复图过滤
-> CLIP / 轻量语义过滤
-> VLM 精分类与结构化识别
```

原因：

- 规则过滤最便宜，适合去掉二维码、页眉 logo、水印、广告图
- `imagehash` 适合去重
- `CLIP` 适合判断“是否像知识图”
- `VLM` 成本最高，应只处理高价值图片


## 3. 数据层设计

### 3.1 三套库并存

建议不要只存 `user_knowledge` 一张表，而是逐步演进为三套存储：

1. `source_chunks`
2. `knowledge_points`
3. `learning_state`

### 3.2 source_chunks

用途：

- 保存原文事实
- 支持引用
- 支持资料搜索
- 支持 RAG 检索

建议字段：

```text
chunk_id
material_id
source_pdf
page_number
source_bbox
subject
chapter_name
chunk_type        # text / table / diagram / image_caption
cleaned_text
raw_text
source_location   # 题号、段落、小节
keywords_json
embedding_ref     # 未来接向量库
```

### 3.3 knowledge_points

用途：

- 保存确认后的正式知识点
- 面向用户复习和知识编辑

建议字段：

```text
knowledge_id
knowledge_name
knowledge_type
subject
chapter_name
core_definition
exam_question_styles
keywords
related_concepts
pitfalls
review_priority
mastery_state
source_chunk_ids
source_page
source_text
source_location
review_content
review_generated_at
```

### 3.4 learning_state

用途：

- 掌握度
- 复习排序
- 错题/追问记录

建议字段：

```text
knowledge_id
user_id
mastery_score
wrong_count
last_reviewed_at
next_review_at
review_interval_days
priority_override
```


## 4. 检索与问答

### 4.1 当前推荐方案

当前阶段最合适的是混合检索，而不是纯向量库：

```text
关键词检索 + 向量检索 + 规则排序
```

建议路线：

短期：

- `SQLite + FTS5`
- 结构化知识点表
- source_chunks 表

中期：

- `Qdrant` 或 `pgvector`
- source_chunks 向量化
- knowledge_points 向量化

长期：

- `RRF` 合并 keyword / vector / HyDE 命中
- 知识点和原文块联合检索

### 4.2 可借鉴的历史原型思路

建议吸收历史原型里的这些设计思路，但不要把工程依赖绑定到工作区外部目录：

- `KnowledgeChunk` 思路
- `Qdrant` 本地磁盘模式
- `HyDE questions` 提高召回
- `RRF` 合并检索
- `LearningStore` 掌握度衰减
- `domains/exam_408/profile.yaml` 领域配置

不建议现阶段整包引入：

- LangGraph 全量图工作流
- MinerU 云依赖直接耦合到现有页面
- 多模态问答主链
- 完整后台任务系统

原因是当前项目首先需要稳住资料入库、引用追溯和 UI 体验，再扩张到复杂 RAG。


## 5. UI 演进方向

### 5.1 当前问题

当前界面存在几个明显问题：

- 首页横幅、指标卡、表单、知识库列表像四套不同的界面拼在一起
- 操作路径偏“表单堆叠”，不够像知识工作台
- 用户对“当前在处理资料、确认知识点、复习知识库”这三种状态感知不清晰
- 原文依据、复习内容、知识点关系缺少统一阅读层级

### 5.2 目标气质

希望整体体验接近“苹果式知识工作台”，不是指做拟物或过度发光，而是：

- 安静
- 克制
- 有层级但不喧闹
- 重点信息突出
- 动线短
- 操作状态清楚

可以借鉴的体验关键词：

- 内容优先
- 轻量玻璃感而不是重卡片
- 少而明确的主操作
- 大量留白
- 文本和引用排版整齐
- 切换有状态，但不花哨

### 5.3 页面结构建议

不建议继续把所有功能放进长页连续表单里。更流畅的结构应是：

```text
左侧：资料与导航
中间：当前主工作区
右侧：引用 / 复习 / 关系侧栏
```

对应三个主视图：

1. 导入资料
2. 确认知识点
3. 知识库工作台

### 5.4 更流畅的工作流界面

推荐改成：

#### A. 导入资料页

布局：

- 顶部极简标题
- 中间大面积拖拽上传区
- 下方实时显示解析状态
- 右侧显示“资料摘要 / 页数 / 提取方式 / 清洗结果”

重点：

- 用户只关心“资料有没有导入好”
- 不要让大段原始文本一上来占满屏幕

#### B. 知识点确认页

布局：

- 左侧：候选知识点列表
- 中间：当前知识点详情编辑
- 右侧：原文依据 / 页码 / 题号 / warning

这会比“一个个 expander 往下堆”更像专业工具。

#### C. 知识库工作台

布局：

- 顶部：学科筛选、搜索、排序、优先级筛选
- 中间：知识点列表
- 右侧：复习内容、原文引用、关系图

用户点击某个知识点后：

- 中间显示知识点摘要
- 右侧显示原文依据
- 下方显示 AI 复习内容
- 可进一步打开“相关知识点”

### 5.5 苹果式 UI 原则在本项目里的具体落点

可以这样落地：

1. 降低大面积高饱和色块
2. 用更细腻的灰阶层级代替大量强边框
3. 指标卡减少“数字看板”味道，改成轻量信息面板
4. 所有主操作按钮控制为 1 个主色 + 1 个次级样式
5. 用分栏和侧栏代替长串展开面板
6. 原文依据和复习内容采用统一阅读容器
7. 只保留极少数高优先级动画，例如切换、展开、保存成功

### 5.6 视觉建议

建议风格：

- 字体：系统中文字体优先，英文部分用系统 sans
- 主色：偏暖中性色 + 一种克制强调色
- 背景：浅灰白分层，而不是一整块纯白
- 圆角：8px 左右，不要过大
- 阴影：浅且软，几乎不可察，只做层级辅助
- 图标：少量线性图标，避免表情化图标充满页面


## 6. 知识关系图方案

用户希望“选定知识点，展示它们之间的联系、概念和综合关系”，建议不要使用普通 AI 生图，而应使用结构化图工具：

推荐顺序：

1. `Mermaid`：先做静态概念图 / mindmap
2. `Cytoscape.js`：做交互式知识图谱
3. `ECharts Graph`：做更强展示型关系图

后端输出应是关系 JSON，而不是直接输出一张图片：

```json
{
  "nodes": [
    {"id": "kmp", "label": "KMP算法", "type": "算法"},
    {"id": "next", "label": "next数组", "type": "核心概念"}
  ],
  "edges": [
    {"source": "kmp", "target": "next", "relation": "依赖"}
  ]
}
```

这比普通“生图”更适合知识库，因为它可点击、可筛选、可联动原文。


## 7. 推荐实施顺序

### 阶段 1：稳住当前系统

- 持续增强文本清洗
- 引用去噪
- 原文依据更完整
- 资料、知识点、上传目录状态一致

### 阶段 2：引入 source_chunks

- 保存清洗后的页级/题级片段
- 绑定 `material_id/page/source_location`
- 支持原文搜索

### 阶段 3：UI 工作台化

- 导入页、确认页、知识库页分工更明确
- 左中右三栏结构
- 统一视觉语言

### 阶段 4：关系图与引用式复习

- 选定知识点生成关系图
- 右侧联动引用和复习内容

### 阶段 5：RAG 增强

- FTS + 向量检索
- Qdrant / pgvector
- HyDE / RRF
- “问我的资料库”


## 8. 结论

这个系统更好的方向，不是继续堆叠 OCR 和知识点抽取按钮，而是把它升级为：

```text
一个围绕专业课资料构建的
可引用、可确认、可复习、可追问、可关系化展示的
私有知识工作台
```

短期最重要的事情有两件：

1. 建立 `source_chunks + knowledge_points + learning_state` 三层结构
2. 把当前界面从“长页面表单”重构为“知识工作台”

这两件事做好之后，MinerU、CLIP、VLM、RAG、关系图都会自然地接到同一条主线里，而不是继续形成拼装式功能堆积。
